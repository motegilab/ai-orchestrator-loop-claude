00 / エグゼクティブサマリ

#0結論と推奨

判断
「Webhookサーバ + Pythonループ」は不要。Claude Codeのネイティブ機能で全部できる。

現在のCODEXベース設計は「AIがコマンドを待つ」受動モデル。Claude CodeはSessionStart / Stop / PostToolUse Hooks + Skills + CLAUDE.mdによって、AIがワークフローを主導するプッシュモデルをネイティブに実現できる。Webhookサーバ（tools/orchestrator/server.py）は削除、Pythonポーリングは削除、makeターゲット12本は3本に削減できる。

⚡

フリクション排除

Hookが全自動化。人間はEscキー以外叩かない。セッション開始→作業→レポート→次回コンテキスト注入が自律的に回る。

🔁

汎用ループ

CLAUDE.md + Skills = PJテンプレ。新PJはcp -r _template/ new-pj/の1コマンドで即スタート。

🏗️

Git-native

runtimeはgit管理外。SSOTはgit管理。PJ間でSkillsは~/.claude/skillsにグローバル共有。完全に現行設計の哲学を継承。

03 / 提案アーキテクチャ

#3Claude-First アーキテクチャ

3.1 全体フロー（v1）

核心原則
「人間がClaude Codeを起動する」のは1回だけ。あとはHookがループを駆動する。 next_prompt.mdを手動で貼り付ける作業は消滅する。

ループ詳細（Hook-driven）

【1】make loop-start └─ claude --add-dir ~/.claude/skills --allowedTools Read,Write,Edit,Bash,Task \ -p "$(cat runtime/logs/next_session.md)" # 初回は next_session.md がなければ CLAUDE.md の冒頭タスクを使う 【2】SessionStart Hook が自動実行 ├─ .claude/hooks/on_session_start.py │ ├─ runtime/runs/latest.json を読む │ ├─ runtime/reports/REPORT_LATEST.md を読む │ └─ stdout に additionalContext を出力 → Claudeの会話に自動注入 【3】UserPromptSubmit Hook └─ .claude/hooks/ssot_gate.py ├─ SSOT整合性チェック（sha256） └─ 違反時: exit 2 → Claude に "SSOT_GATE: BLOCKED" を返す 【4】Claude が作業（Observe → Patch → Verify） ├─ Skills が自動invoke（observe/patch/verify/report） └─ PostToolUse Hook → フォーマット / 品質ゲート / 監査ログ 【5】Stop Hook が自動実行 ├─ .claude/hooks/on_stop.py │ ├─ runs/YYYY-MM-DD_runNNN.json 生成 │ ├─ runs/latest.json 更新 │ ├─ reports/REPORT_LATEST.md 生成 │ └─ logs/next_session.md 生成 ← 次回SessionStartで注入される └─ 次回 make loop-start で自動的に前回の続きから始まる

05 / マルチPJ管理

#5新PJへの展開方法

設計方針
このリポジトリ自体をテンプレートリポジトリとして使う。新PJは「クローン → CLAUDE.md書き換え → SSOT.md書き換え → loop-start」の4ステップで即スタート。

Skills の2層構造

🌐

グローバルSkills（~/.claude/skills/）

全PJで共通のSkill。observe / patch / verify / reportといったコアワークフロー。一度書けばどのPJでも使える。更新は中央管理。

📁

PJ固有Skills（.claude/skills/）

そのPJだけのSkill。UnityビルドやGASデプロイなどPJ特有の手順。テンプレートにはプレースホルダのみ置く。

新PJ展開フロー

# 1. テンプレートからクローン gh repo create my-new-project --template org/ai-orchestrator-loop # 2. PJ固有情報を書く（2ファイルだけ） vim CLAUDE.md # PJの目的・技術スタック・key commands vim SSOT.md # PJ固有の絶対ルール・スコープ # 3. policy/ssot_integrity.jsonのhashを更新 python .claude/hooks/ssot_gate.py --update-hash # 4. ループスタート make loop-start

PJ間での状態管理

スコープ場所内容
PJ内状態runtime/runs/latest.json最新ループの結果（git管理外）
PJ内履歴runtime/runs/YYYY-MM-DD_*.json全ループ履歴（git管理外）
PJ設計SSOT.md + CLAUDE.md設計の正本（git管理）
全PJ共通手順~/.claude/skills/グローバルSkills（別リポジトリ管理推奨）

#6新SSOT 全文（Claude-first v1.0）

このSSOTについて
以下が実際にリポジトリのルートに置くSSOT.mdの内容です。旧SSOTの哲学・ルールを全て継承しつつ、Claude Codeネイティブ機能に最適化されています。

SSOT: Claude-First AI Orchestrator Loop

NS_ID: NS_AI_ORCHESTRATOR_LOOP_CLAUDE_SSOT
バージョン: 1.0（Claude-first / Hook-driven）
最終更新: 2026-03-05
前バージョン: SSOT v2.0（CODEX版, 2026-02-18）

§0 設計原則

Claude-FirstClaude Code CLIが唯一の実行エンジン。WebサーバもPollingも持たない。
Hook-Driven Loopループ制御はSessionStart / Stop / PreToolUse / PostToolUse Hookが担う。Pythonサーバは不要。
汎用性任意のPJワークスペース（Unity / GAS / NSS 等）で動く。テンプレートリポジトリとして機能する。
Files-as-Memory状態管理はファイル（JSON/MD）で完結。DBもキャッシュも持たない。
SSOT-First必ずSSO.md を読んでから実行する。SSOTはUserPromptSubmit Hook で強制される。
1原因1修正1ループで修正するのは1原因に起因する1修正のみ。スコープ拡大は禁止。
監査ログが真実runtime/runs/latest.json とREPORT_LATEST.md が唯一の真実。
Human Tool哲学Human Tool（arxiv 2602.12953）— AIがワークフロー主導。人間はmake loop-start を叩くだけ。

§1 絶対ルール（v1）

NEVER
これらはHookで確定的に（100%）ブロックされる。CLAUDE.mdへの記述は「確率的」であるため不十分。
  • SSOT.mdを自動ループ内で編集しない（SSOT更新は手動のみ）
  • policy/ssot_integrity.jsonを自動ループ内で編集しない
  • runtime/以外にランタイム生成物を置かない
  • .git/以下への直接書き込みをしない
  • 外部APIへのネットワーク接続をしない（v1スコープ）
  • 大規模リファクタリングを1ループで実施しない（スコープ外）
  • タイムアウト時を「成功」として記録しない（必ずfailedと記録する）

§1.1 許可される実行入口（v1）

コマンド動作
make loop-startClaude Code CLIを起動。runtime/logs/next_session.mdを初期プロンプトとして渡す
make loop-statusruntime/runs/latest.json と REPORT_LATEST.md を表示
make loop-stop実行中のClaudeセッションを終了（Escと同等）

§3 ループ仕様（Hook-Driven）

ループの定義: make loop-start 実行 → SessionStart Hook発火 → Claude作業 → Stop Hook発火 → runtime更新 → 次回make loop-startで継続、をもって「1ループ」とする。

§3.1 SessionStart Hook（on_session_start.py）

必須動作（順番固定）:

  1. 環境チェック（Python / SSOT.md / policy/ の存在確認）
  2. runtime/runs/latest.json を読む（存在しない場合はスキップ）
  3. runtime/reports/REPORT_LATEST.md を読む（存在しない場合はスキップ）
  4. runtime/logs/next_session.md を読む（存在しない場合はスキップ）
  5. 上記3ファイルの要約を stdout に出力（Claude の additionalContext に注入される）

§3.2 Stop Hook（on_stop.py）

必須動作（順番固定）:

  1. セッションログから実行サマリを抽出
  2. runtime/runs/YYYY-MM-DD_runNNN.json を生成
  3. runtime/runs/latest.json を更新
  4. runtime/reports/REPORT_LATEST.md を生成（失敗時はREPORT_FAILED.mdに記録）
  5. runtime/logs/next_session.md を生成（次回SessionStartで使用）

⚠️ Stop Hookのstop_hook_activeフィールドを確認してexit 0すること（無限ループ防止）。

§3.3 PreToolUse Hook（ssot_gate.py）

  • matcher: Write|Edit|MultiEdit
  • 対象ファイルが絶対ルール（§1）に違反する場合: exit 2 でブロック、stderr に理由を出力
  • SSOT.mdへの書き込み試行: 常にブロック
  • policy/ssot_integrity.jsonのhashと実ファイルが不一致: exit 2

§3.4 PostToolUse Hook（post_tool_quality.py）

  • matcher: Write|Edit
  • 全ツール実行を runtime/artifacts/audit_log.jsonl に記録（追記）
  • Pythonファイル書き込み後: 構文チェック（py_compile）
  • Markdownファイル書き込み後: 必須セクションチェック（レポート類のみ）

§4 Hooks設定（.claude/settings.json 必須内容）

{ "hooks": { "SessionStart": [{ "hooks": [{ "type": "command", "command": "python .claude/hooks/on_session_start.py" }] }], "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "python .claude/hooks/ssot_gate.py --mode=prompt" }] }], "PreToolUse": [{ "matcher": "Write|Edit|MultiEdit", "hooks": [{ "type": "command", "command": "python .claude/hooks/ssot_gate.py" }] }], "PostToolUse": [{ "matcher": "Write|Edit", "hooks": [{ "type": "command", "command": "python .claude/hooks/post_tool_quality.py" }] }], "Stop": [{ "hooks": [{ "type": "command", "command": "python .claude/hooks/on_stop.py", "timeout": 60 }] }] } }

§5 Skills仕様

Skillsは自動invoke対応にする。descriptionを精密に書くことで、Claudeが状況を判断してSkillを自動的に使用する。

Skill名置き場自動invokeのトリガ主要outputs
observe ~/.claude/skills/observe/ エラー・問題の調査依頼時 / REPORT_LATEST.mdに問題記録がある時 issue_candidates.md, evidence_paths
patch ~/.claude/skills/patch/ ファイル修正・実装依頼時 / observeの結果を受けて修正に入る時 diff summary, files_changed
verify ~/.claude/skills/verify/ patchの後 / 「確認して」「テストして」と言われた時 exit_codes, stdout_tail, evidence_paths
report ~/.claude/skills/report/ 作業終了時 / Stopの直前 REPORT_LATEST.md, runs/latest.json

SKILL.md必須セクション（全Skillsに必要）:

  • MUST READ FIRST（前提ファイル）
  • Inputs（受け取る情報）
  • Steps（実行手順）
  • Outputs（生成するファイル・artifact paths）
  • Failure modes / remediation

§7 レポート仕様（runs/*.json 必須項目）

旧SSOTの §5 を継承。以下フィールドは全て必須:

{ "run_id": "2026-03-05_run001", // 日付+連番 "session_id": "...", // Claude CodeのセッションID "started_at": "ISO8601", "stopped_at": "ISO8601", "source": "claude-code-cli", "intent": "task_completed|task_failed|blocked", "summary": "短文（50字以内）", "status": "success|failed|blocked", "top_errors": [], // 失敗時のみ。最大5件 "evidence_paths": [], // 生成したファイルのパス一覧 "report_status": "success|failed", "report_path": "runtime/reports/REPORT_LATEST.md", "next_session_path": "runtime/logs/next_session.md" }

§7.1 next_session.md テンプレ（必須）

旧SSOTの §6 を継承。Stop Hookが生成。必ず以下のセクションを含む:

  • DONE: ここまでやった（今回セッション要約）
  • NEXT: 次にやること（推奨手順）
  • FAIL: ここで落ちた（失敗時のみ。エラー抜粋）
  • FIX: 推論して直して（最小差分・禁止範囲・1原因1修正）
  • VERIFY: 再検証（make verify / make smoke等）
  • CONTEXT: 次回セッション開始時に必要な状態情報

§8 マルチPJ管理

このリポジトリはGitHubのテンプレートリポジトリとして機能する。

  • 新PJ作成: gh repo create NEW-PJ --template THIS-REPO
  • PJ固有設定: CLAUDE.md と SSOT.md の2ファイルのみ書き換える
  • グローバルSkills: ~/.claude/skills/ に置き全PJで共有する（別リポジトリで管理推奨）
  • PJ固有Skills: .claude/skills/ に置く
  • runtime/は各PJに独立して存在する（git管理外）

08 / 判断の根拠

#8各判断の根拠

なぜWebhookサーバを削除するのか

Claude CodeのStopフックは「Claude Code agentが応答を完了した時」に発火する。これはCursorのWebhookと機能的に等価であり、かつPythonサーバの起動・管理・ポート管理が不要になる。フリクションの排除という要件に直結する。

なぜnext_prompt.mdを手動貼り付けしなくていいのか

SessionStartフックのstdoutは自動的にClaudeの会話コンテキストにadditionalContextとして注入される（Claude Code v2以降）。これによりnext_session.mdの内容を「セッション開始時に自動的にClaudeが読む」動作が実現する。

なぜHookはCLAUDE.mdより強いのか

CLAUDE.mdの指示は確率的（〜70%）。PreToolUseフックにexit 2を返すスクリプトを置けば確定的（100%）にブロックできる。SSOTゲートはHookで実装することで初めて「絶対ルール」として機能する。

なぜSkillsのdescriptionが重要なのか

Skillsの自動invokeはdescriptionの精度に依存する。曖昧なdescriptionはあらゆるタスクでSkillを発火させてしまう。「observe: 問題調査時、REPORT_LATEST.mdにエラーがある時」のように、ファイル名・ディレクトリ・状況を明示したdescriptionが必要。

最後に
既存のSSOT（v2.0）の設計思想・哲学・ルールは全て正しく、全て継承されています。変わったのは「実装レイヤだけ」です。CODEXが「Claudeにコマンドを渡す」外部制御モデルだったのに対し、Claude Codeは「ClaudeがHookを通じてワークフローを自律的に駆動する」内部制御モデルです。この違いがフリクションゼロ・汎用性・マルチPJ対応を同時に実現します。
